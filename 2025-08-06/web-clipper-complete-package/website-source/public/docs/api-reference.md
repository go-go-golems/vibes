# Web Clipper Extension - Native Messaging API Reference

## Overview

The Web Clipper Extension utilizes the browser's native messaging API to establish secure communication between the browser extension and the local backend service. This architecture ensures that all data processing and storage occurs locally on the user's machine, maintaining complete privacy and control over personal information.

This comprehensive API reference documents the communication protocol, message formats, error handling, and implementation details necessary for understanding, maintaining, or extending the Web Clipper Extension system.

## Native Messaging Architecture

### Communication Model

Native messaging provides a standardized method for browser extensions to communicate with local applications through a secure, process-isolated channel. The Web Clipper Extension implements this pattern using the following components:

**Browser Extension**: The frontend component running within the browser context, responsible for user interface presentation, content extraction, and message formatting.

**Native Messaging Host**: A manifest file that describes the local application and defines communication parameters, installed in browser-specific directories.

**Backend Service**: A Go application that receives messages from the browser, processes clip data, and manages local file storage.

### Security Model

The native messaging architecture provides several security benefits:

**Process Isolation**: The browser and backend service run in separate processes, preventing direct memory access or code injection between components.

**Permission-Based Access**: The browser extension must explicitly request native messaging permissions, and users can review and revoke these permissions at any time.

**Manifest Validation**: Browsers validate native messaging host manifests before allowing communication, ensuring that only authorized applications can receive messages.

**Message Size Limits**: The protocol enforces message size limits to prevent resource exhaustion attacks or accidental memory consumption.

## Message Protocol Specification

### Message Format Structure

All communication between the browser extension and backend service uses JSON-formatted messages with a standardized structure. The protocol supports both request-response patterns and asynchronous notifications.

#### Standard Message Envelope

```json
{
  "action": "string",
  "data": {
    // Action-specific payload
  },
  "metadata": {
    "timestamp": "ISO8601 timestamp",
    "version": "protocol version",
    "requestId": "unique identifier"
  }
}
```

**action**: A string identifier specifying the requested operation. Currently, the system supports the "saveClip" action, with extensibility for future operations.

**data**: An object containing the action-specific payload. The structure varies based on the action type but follows consistent patterns for similar data types.

**metadata**: Optional envelope information including timestamps, protocol versions, and request identifiers for debugging and logging purposes.

### Message Size Constraints

The native messaging protocol imposes specific size limitations that applications must respect:

**Maximum Message Size**: 1,048,576 bytes (1 MB) per message, enforced by the browser's native messaging implementation.

**Practical Limits**: While the theoretical limit is 1 MB, practical message sizes should remain well below this threshold to ensure reliable transmission and processing.

**Content Truncation**: The Web Clipper Extension automatically truncates extremely long text selections to prevent message size violations while preserving the most relevant content.

## SaveClip Action Specification

### Request Format

The saveClip action represents the primary operation of the Web Clipper Extension, capturing web content and associated metadata for local storage.

```json
{
  "action": "saveClip",
  "data": {
    "timestamp": "2025-08-06T12:00:00.000Z",
    "url": "https://example.com/article",
    "title": "User-defined clip title",
    "category": "TIL|article|thought|quote",
    "selectedText": "Text selected by user on the webpage",
    "note": "User-provided notes and commentary",
    "pageTitle": "Original webpage title",
    "domain": "example.com"
  }
}
```

#### Field Specifications

**timestamp**: ISO 8601 formatted timestamp indicating when the clip was created. Generated by the browser extension using the user's local timezone. Used for chronological organization and debugging purposes.

**url**: Complete URL of the webpage being clipped, including protocol, domain, path, and query parameters. Must be a valid HTTP or HTTPS URL. Used as the primary identifier for the source content.

**title**: User-defined title for the clip, typically customized from the original page title to improve organization and searchability. Limited to 200 characters to ensure filesystem compatibility.

**category**: One of four predefined categories that determine the organizational structure and intended use of the clip:
- `TIL`: Today I Learned - for factual discoveries and learning moments
- `article`: Long-form content requiring deeper analysis
- `thought`: Personal reflections and analytical insights
- `quote`: Memorable passages and notable quotations

**selectedText**: Text content selected by the user on the webpage before activating the extension. May be empty if no text was selected. Automatically truncated if it exceeds reasonable length limits.

**note**: Free-form text provided by the user to add context, analysis, or personal commentary to the clip. This field supports markdown formatting and has no strict length limits, though extremely long notes may impact performance.

**pageTitle**: The original title of the webpage as defined in the HTML `<title>` element. Preserved for reference and comparison with the user-defined title.

**domain**: Extracted domain name from the URL, used for organizational purposes and quick identification of content sources.

### Response Format

The backend service responds to saveClip requests with a standardized response format indicating success or failure:

#### Success Response

```json
{
  "success": true,
  "message": "Clip saved successfully",
  "data": {
    "filename": "TIL-user-defined-clip-title.md",
    "filepath": "/path/to/clips/2025-08-06/TIL-user-defined-clip-title.md",
    "size": 1024
  }
}
```

**success**: Boolean flag indicating successful processing and storage of the clip.

**message**: Human-readable description of the operation result, suitable for display to users or logging purposes.

**data.filename**: The generated filename for the stored clip, following the naming convention `[category]-[sanitized-title].md`.

**data.filepath**: Complete filesystem path where the clip was stored, useful for debugging and verification purposes.

**data.size**: Size of the generated markdown file in bytes, providing feedback about the storage impact of the clip.

#### Error Response

```json
{
  "success": false,
  "message": "Detailed error description",
  "error": {
    "code": "ERROR_CODE",
    "details": "Additional technical information"
  }
}
```

**success**: Boolean flag set to false for all error conditions.

**message**: User-friendly error description explaining what went wrong and potentially how to resolve the issue.

**error.code**: Machine-readable error code for programmatic error handling and debugging.

**error.details**: Additional technical information about the error, including stack traces or system error messages when appropriate.

## Error Handling and Status Codes

### Error Classification

The Web Clipper Extension implements a comprehensive error handling system that categorizes errors by type and severity:

#### Validation Errors

**INVALID_ACTION**: The requested action is not recognized or supported by the backend service.

**MISSING_REQUIRED_FIELD**: A required field in the request data is missing or empty.

**INVALID_FIELD_FORMAT**: A field contains data in an incorrect format (e.g., invalid timestamp or URL).

**FIELD_TOO_LONG**: A field exceeds the maximum allowed length for that data type.

#### Storage Errors

**FILESYSTEM_ERROR**: General filesystem operation failed, such as directory creation or file writing.

**PERMISSION_DENIED**: The backend service lacks necessary permissions to write to the clips directory.

**DISK_FULL**: Insufficient disk space to store the clip file.

**FILE_EXISTS**: A clip with the same filename already exists (rare due to timestamp-based naming).

#### System Errors

**BACKEND_UNAVAILABLE**: The backend service is not running or not responding to messages.

**MESSAGE_TOO_LARGE**: The request message exceeds the native messaging size limits.

**PROTOCOL_ERROR**: Communication protocol violation or malformed message structure.

**INTERNAL_ERROR**: Unexpected error within the backend service, typically indicating a bug or system issue.

### Error Recovery Strategies

The extension implements several strategies for handling and recovering from errors:

**Automatic Retry**: Transient errors like temporary filesystem issues trigger automatic retry attempts with exponential backoff.

**User Notification**: All errors result in user-visible notifications explaining the problem and suggesting resolution steps.

**Graceful Degradation**: When possible, the system attempts to save partial information rather than failing completely.

**Logging and Debugging**: Comprehensive error logging helps diagnose issues and improve system reliability.

## Backend Implementation Details

### Go Service Architecture

The backend service is implemented in Go, chosen for its excellent concurrency support, cross-platform compatibility, and efficient binary compilation. The service architecture includes several key components:

#### Message Processing Pipeline

**Input Validation**: All incoming messages undergo strict validation to ensure data integrity and security.

**Content Processing**: Text content is sanitized and formatted for markdown storage while preserving user intent.

**File Generation**: Markdown files are generated using templates that ensure consistent formatting and metadata inclusion.

**Storage Management**: Files are organized into date-based directories with automatic directory creation as needed.

#### Concurrency and Performance

The Go implementation leverages goroutines for concurrent processing while maintaining data consistency:

**Message Handling**: Each incoming message is processed in a separate goroutine to prevent blocking.

**File I/O**: Disk operations use buffered I/O and atomic writes to ensure data integrity.

**Resource Management**: The service implements resource limits to prevent memory exhaustion or disk space abuse.

### File Format Specification

The backend generates markdown files with a standardized format that balances human readability with machine parseability:

```markdown
# [User-defined Title]

**URL**: [Original URL]
**Date**: [Timestamp in human-readable format]
**Category**: [Selected category]
**Domain**: [Extracted domain]

## Selected Text

[User-selected text content, if any]

## Notes

[User-provided notes and commentary]

---

*Clipped on [timestamp] from [domain]*
*Original page title: [pageTitle]*
```

This format provides:
- Clear visual hierarchy for human readers
- Consistent metadata placement for automated processing
- Markdown compatibility for integration with documentation systems
- Preservation of all captured information

## Extension Implementation Details

### Browser Extension Architecture

The browser extension consists of three main components, each serving specific roles in the clipping workflow:

#### Content Script

The content script runs in the context of web pages and is responsible for:

**Text Selection Detection**: Monitoring user text selections and capturing selected content when the extension is activated.

**Page Metadata Extraction**: Gathering information about the current page, including title, URL, and domain.

**DOM Interaction**: Interfacing with the webpage's Document Object Model to extract content and metadata.

#### Background Script

The background script manages extension lifecycle and communication:

**Native Messaging**: Establishing and maintaining communication with the local backend service.

**Message Routing**: Coordinating communication between content scripts, popup interface, and backend service.

**Error Handling**: Managing error conditions and providing user feedback for communication failures.

#### Popup Interface

The popup interface provides the user-facing clipping form:

**Form Management**: Presenting input fields for title, category, and notes while displaying captured content.

**User Interaction**: Handling form submission, validation, and user feedback display.

**State Management**: Maintaining form state and user preferences across clipping sessions.

### Cross-Browser Compatibility

The extension is designed to work across multiple browser platforms with minimal modification:

#### Manifest Differences

**Chrome (Manifest V3)**: Uses the latest manifest format with enhanced security features and service worker architecture.

**Firefox (Manifest V2)**: Maintains compatibility with Firefox's extension system while providing identical functionality.

#### API Abstraction

The extension code abstracts browser-specific APIs to ensure consistent behavior:

**Native Messaging**: Uses browser-agnostic native messaging APIs with fallback handling for browser differences.

**Storage APIs**: Implements consistent local storage behavior across different browser storage systems.

**Permission Handling**: Manages permission requests and validation in a browser-neutral manner.

## Security Considerations

### Threat Model

The Web Clipper Extension operates under a specific threat model that influences security design decisions:

#### Trusted Local Environment

The system assumes that the user's local machine is trusted and secure:

**Local Storage Security**: Clips are stored as plain text files, relying on operating system security for access control.

**Process Security**: The backend service runs with user privileges and trusts the local browser installation.

**Network Isolation**: No network communication occurs, eliminating remote attack vectors.

#### Browser Security Boundary

The extension respects browser security boundaries:

**Same-Origin Policy**: Content extraction respects browser same-origin restrictions.

**Permission Model**: The extension requests minimal permissions and operates within browser security constraints.

**Sandboxing**: Browser extension sandboxing provides isolation from other web content and extensions.

### Security Best Practices

#### Input Validation

All user input undergoes strict validation:

**Content Sanitization**: User-provided content is sanitized to prevent injection attacks in generated files.

**Length Limits**: Input fields have reasonable length limits to prevent resource exhaustion.

**Format Validation**: URLs, timestamps, and other structured data are validated for correct format.

#### File System Security

File operations follow security best practices:

**Path Validation**: File paths are validated to prevent directory traversal attacks.

**Atomic Operations**: File writes use atomic operations to prevent corruption or partial writes.

**Permission Checking**: The service verifies write permissions before attempting file operations.
